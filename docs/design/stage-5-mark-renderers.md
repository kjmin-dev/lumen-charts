# Canvas 2D and WebGPU roadmap for scatter and heatmap

**Implementation status.** Canvas 2D, explicit WebGPU and opt-in adaptive selection are integrated in the chart. The six steps below record the original delivery plan. Desktop qualification is complete for the configurations in the [chart report](../benchmarks/integrated-mark-renderers.md). Physical Android qualification remains open. The WebGPU measurements come from isolated mark layers on Apple M1 in headless Chromium. Canvas 2D is the default and fallback for both series. Candles, axes, labels, drawings and custom primitives continue through the existing pane compositor. WebGL2 supplies a benchmark control. [Current implementation](stage-5-heatmap-scatter.md) · [Prototype results](../benchmarks/mark-fast-paths.md)

## 3. Architecture and public contract

- The chart-level runtime preference `markRenderer` accepts `'canvas2d'`, `'webgpu'` and `'auto'`. Each mark series exposes the requested preference, effective backend and fallback reason through `renderer()`. A WebGPU series may use a 2D dirty patch. Diagnostics should distinguish the series backend from that per-frame shortcut. Treat the preference as host configuration across save and restore.
- Keep the engine's mark window, level of detail (LOD), autoscale and hit queries shared. Give both renderers the same visible rows, dirty ranges, time and price projections, palette, pane dimensions and pixel ratio. Select a backend at the mark-series draw boundary. The existing pane owns compositing and layer order. [Mark series](../../packages/core/src/marks/series.ts) · [Time mapping](../../packages/core/src/marks/time-map.ts)
- Serve the first frame with Canvas 2D while WebGPU loads. Share the GPU device and reusable pipelines across charts on a page. Keep buffers and cached images scoped to their series. On initialization failure or device loss, redraw the latest authoritative window with Canvas 2D. Ignore late initialization or upload completions after a series is removed or its window is replaced. [WebGPU device loss](https://www.w3.org/TR/webgpu/#dom-gpudevice-lost)

## 9. Workload choices and release checks

| Workload                                      | First path to integrate                                                     | Evidence or constraint                                                                                                                                                                                          |
| --------------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Repeated horizontal zoom on dispersed scatter | WebGPU tiles where the index can be reused                                  | At 100k points, GPU p95 was 0.459 ms with tiles and 0.852 ms with columns. The tile index cost about 5.18 ms and 494 kB to build and upload on the M1. Vertical reprojection requires reindexing or a fallback. |
| Dense scatter burst                           | WebGPU column kernel                                                        | At 1M clustered points, columns took 1.442 ms and tiles 3.211 ms. Visible density and distribution belong in the selection criteria.                                                                            |
| Fixed heatmap pan / changing color range      | Translate a valid cached image / recolor the scalar texture in a GPU shader | Cache reuse benefited both backends. A varying color range invalidates a precolored bitmap. Fractional motion and irregular or logarithmic grids need the general path until verified.                          |
| Single point or column                        | Dirty patch on the owning layer                                             | Allow a direct patch only when its coverage, opacity and z-order permit it. Otherwise recompose the affected layer. Measure the next full redraw to include any deferred uploads.                               |

The 100k–300k tile and 1M column results are prototype test cases. The release decision uses real data ingestion, projection, uploads and composition. Keep render bundles, immediate data and extra GPU texture copies experimental until an integrated workload justifies them. [Scatter and update results](../benchmarks/mark-fast-paths.md) · [Heatmap cache and color-range results](../benchmarks/heat-range.md)

- **Correctness.** Compare public-API output on the same input for pan, fractional zoom, resize/DPR, palette changes, overlapping points, transparent cells and updates followed by redraw. Repeat with logarithmic price axes, session gaps, multiple series and budget-driven layer merging. Verify state restore, autoscale and heatmap value queries through backend changes.
- **Performance.** Apply the existing whole-chart frame JS p95 budgets of 8 ms for pan/zoom and 4 ms for update frames. Prioritize 300k dispersed scatter zoom and 1.44M-cell heatmap pan/zoom, where the current chart exceeds budget. Record GPU pass time separately, plus compositor cadence, first usable frame, cold index build, deferred flush and peak bytes. Compare both backends with the same cache and patch opportunities. [Production baseline and budgets](../benchmarks/stage-5-heatmap-scatter.md)
- **Resource use and recovery.** Charge retained bitmaps and GPU resources against explicit budgets. Exercise several charts sharing a device, loss during a burst, rapid destroy/recreate and memory pressure. Verify that the latest chart data survives and released charts relinquish their resources.

## Implementation decisions

- The shared heatmap geometry supplies the same integer boundaries and subpixel reduction ranges to both backends. Canvas and GPU can translate an existing image only after checking the overlapping source columns and every price-row range. Exposed columns are redrawn. A fixed camera and dirty data update their affected region.
- The integrated scatter uses the CPU time map and binary64 boundary checks before handing row indices to the GPU. Prices use the same JS projection and rounding as the Canvas oracle. The two compute kernels cover clipped square stamps and original row order. Indexing considers the size of the held window and concentration on the visible time axis. Unsupported styles render with Canvas.
- The page owns the device and pipelines until the final lease is released. Per-series buffers and retained canvases count against the shared four-byte-unit rendering budget. Late initialization, failed requests, lost devices and unsupported limits have a Canvas path.
- Adaptive selection considers visible rows at the chosen LOD. The initial trial floors are 100k scatter points and 240k heatmap cells. Three accumulated costly full Canvas draws (6 ms or more) start a trial. The series compares smoothed full-frame mark work, gives the GPU six samples to show a 15% improvement, and accounts for first-draw switching debt over sixteen samples. Eight full draws below half the density floor or a failed trial return to Canvas with a thirty-full-draw cooldown. These are host observations and provisional desktop calibration values.
